  - **Decision:** Preserve payment validation and both foreign keys. - Corrected amount presentation in the [reconciliation planner](BancoAlimentar.AlimentaEstaIdeia.Web/Migrations/Scripts/MergeDuplicateEasyPayPaymentIds.sql), with fractional-currency coverage in the [regression tests](scripts/Test-EasyPayPaymentReconciliation.ps1).
  - **Context:** SQL `real` values serialized to scientific notation such as `6.9999999e-001` for a payment intended as EUR 0.70, making the review plan misleading to read.
  - **Options considered:** Change database storage to decimal, round all comparisons/hashes, or cast only review-plan amount projections to fixed decimal numbers.
  - **Decision:** Export `Requested` and `Paid` as `decimal(19,4)` JSON numbers. Retain raw database values, equality checks, and evidence hashes; presentation rounding must not turn a stored mismatch into an approved match. Four decimals preserve sub-cent review detail and align with the existing confirmation comparison scale. Changing monetary storage is separate work.
  - **Rollout:** New plans use decimal presentation automatically. The local review plan's amount fields were refreshed against unchanged database evidence without changing approvals or hashes. No database rows/schema were modified; existing approvals still require explicit review.
- Hardened transaction handling in [MergeDuplicateEasyPayPaymentIds.sql](BancoAlimentar.AlimentaEstaIdeia.Web/Migrations/Scripts/MergeDuplicateEasyPayPaymentIds.sql).
  - **Context:** The dry-run script rolled back on success but had no explicit cleanup for catchable errors and could roll back unrelated work if run inside an existing transaction.
  - **Options considered:** Replace the reconciliation with a read-only preview, or retain the transactional simulation with an existing-transaction guard and error handling.
  - **Decision:** Keep transactional reconciliation and default `@DryRun = 1`. Reject existing transactions with an informational `RAISERROR` (severity 10) and `RETURN` before enabling `XACT_ABORT`. The guard deliberately does not raise an exception: `THROW` honors `XACT_ABORT`, and a severity-16 error crossing a dynamic SQL boundary can leave the caller's transaction uncommittable. Commit only when `@DryRun = 0`; otherwise roll back. Catch errors, roll back any active script transaction, and rethrow the original error.
  - **Rollout:** Run the entire script per tenant on a connection without an active transaction. Review the default dry-run output before explicitly setting `@DryRun = 0` and rerunning. Dry runs still execute writes and triggers before rollback; external side effects are not guaranteed to be reversible. Cancellation and connection-level failures may bypass `CATCH`; after cancellation, check the session for an open transaction before reusing it.

### Decision: reconcile duplicate `EasyPayPaymentId` values before `HardenPaymentConcurrency`
- **Context:** Migration `20261024174319_HardenPaymentConcurrency` adds the unique filtered index `IX_Payments_EasyPayPaymentId`. It first checks for duplicates and throws SQL error `51000` ("Duplicate EasyPayPaymentId values must be reconciled before applying HardenPaymentConcurrency.") if any exist. The earlier reconciliation script deleted duplicate payment and notification rows and changed donation links; the revised script must preserve that history.
- **Options considered:**
  1. Merge duplicate rows, deleting the extras and redirecting foreign keys.
  2. Replace duplicate identifiers with placeholders or pack historical values into unrelated application columns.
  3. Preserve all rows and relationships, archive the original provider identifiers in a dedicated audit table, and clear only the conflicting identifiers. **(chosen)**
- **Decision:** Keep the migration's safety checks unchanged. In [MergeDuplicateEasyPayPaymentIds.sql](BancoAlimentar.AlimentaEstaIdeia.Web/Migrations/Scripts/MergeDuplicateEasyPayPaymentIds.sql), keep one canonical provider-ID owner and set only the other payments' `EasyPayPaymentId` to `NULL`. The filtered unique index permits multiple nulls. Use `UPDATE ... OUTPUT INTO` to atomically retain each changed `PaymentId`, `CanonicalPaymentId`, `OriginalEasyPayPaymentId`, and `ReconciledAtUtc` in `dbo.EasyPayPaymentIdReconciliationAudit`; do not overwrite existing audit records. No other payment fields, notifications, donation confirmations, or foreign keys are changed. This preserves history but does not correct any pre-existing accounting inconsistencies; provider-ID lookups resolve only to the canonical payment.
- **Reconciliation rules:**
  - Canonical payment per `EasyPayPaymentId`: selected by an explicitly approved JSON plan. Confirmation-backed rules propose owners; date-based ranking is informational only for flagged groups and cannot approve an exception.
  - Stop the entire transaction for incomplete, stale, or invalid approval evidence; do not partially reconcile other groups. Multiple completions and missing links can proceed only through a reviewed plan, not by bypassing validation.
  - Create audit tables only when there are identifiers to clear. Table creation and audit inserts are transactional, so a dry run leaves no new tables or records behind. Existing per-payment history is not overwritten; consumed plans must be regenerated rather than replayed.
  - Defaults to read-only `@Mode = N'Plan'`. Reconcile mode retains `@DryRun = 1`; only an explicit zero commits a fully approved plan.
- **Rollout:** Follow the [approval workflow](Documentation/EasyPay-Payment-Reconciliation-Workflow.md) separately per tenant. Pause writers before dry-run/apply, review the complete generated plan, resolve exceptions, and explicitly approve owners/reasons. Keep both committed audit tables as reconciliation history, then apply pending migrations in order. Other identifier-length or invoice-sequence problems must be fixed separately. Dry runs still execute writes and triggers before rollback, and cancellation may bypass `CATCH`.
