### Fixed
- Fixed tenant migration compilation and runtime configuration readiness in [tenant middleware](BancoAlimentar.AlimentaEstaIdeia.Sas.Core/Middleware/DoarTenantMiddleware.cs), the [host-wide configuration cache](BancoAlimentar.AlimentaEstaIdeia.Sas.ConfigurationProvider/KeyVaultConfigurationCache.cs), and [settings reload](BancoAlimentar.AlimentaEstaIdeia.Web/Areas/Admin/Pages/ReloadSettings.cshtml.cs). See [tenant configuration guidance](Documentation/Tenant-Configuration.md).
  - **Context:** Two `TenantDomainOwnership` implementations caused `CS0111`. Cached or startup-preloaded secrets bypassed database readiness and retries; static configuration caches survived settings reload, and transient managers did not coordinate bootstrap.
  - **Options considered:** Keep both migration implementations under different names, clear static dictionaries in place, or retain only the guarded migration and coordinate configuration through a host-owned, replaceable cache.
  - **Decision:** Remove the obsolete duplicate and retain [the guarded migration](BancoAlimentar.AlimentaEstaIdeia.Sas.Model/Migrations/20261101120201_TenantDomainOwnership.cs), including its data checks and deployed identity key lengths. Await tenant initialization on every configured request. Share bootstrap and per-tenant secret-load coordination within one host and atomically replace the cache on reload so old loads cannot restore stale credentials. Authentication provider registration remains host-wide.
  - **Rollout:** This fix retains the guarded domain migration and does not rewrite data. Audit domain/environment mappings and apply pending infrastructure migrations through the ordered deployment step. Shared invalidation in the following entry supersedes the requirement to reload each application instance manually. Successful tenant seeding is not rerun by settings reload.
- Stopped integration test hosts from exhausting Linux inotify instances by enabling polling file watchers in [TestFileWatching](BancoAlimentar.AlimentaEstaIdeia.Web.TestHost/TestFileWatching.cs), applied by [CustomWebApplicationFactory](BancoAlimentar.AlimentaEstaIdeia.Web.TestHost/CustomWebApplicationFactory.cs) and [BrowserTestApplication](BancoAlimentar.AlimentaEstaIdeia.Web.TestHost/BrowserTestApplication.cs), with a [regression test](BancoAlimentar.AlimentaEstaldeia.Web.IntegrationTests/BasicTests.cs).

In a Linux container with polling unset, as on the agent, held inotify instances grew steadily from 0 to 103 and were never released.
  - **Options considered:** Set `DOTNET_USE_POLLING_FILE_WATCHER` only in the pipeline; raise `fs.inotify.max_user_instances` on the shared Docker host; fix disposal of every per-test host; or enable polling in the shared test host.
  - **Decision:** Enable polling in the test host before any `PhysicalFileProvider` is created, preserving explicit values. This protects CI jobs, browser tests, and local Linux runs without host administration or changes across about 30 test files. The same Linux run then held 0 inotify instances and passed all Integration tests.
  - **Rollout:** None; this changes only test code. Raising the host's inotify limit remains optional headroom for other workloads.

- Addressed the non-Azure subscription review issues in [capture persistence](BancoAlimentar.AlimentaEstaIdeia.Repository/SubscriptionRepository.cs), [failure-email delivery](BancoAlimentar.AlimentaEstaIdeia.Web/Api/EasyPayGenericNotification.cs), and the [reconciliation report](BancoAlimentar.AlimentaEstaIdeia.Tools/EasyPay/SubscriptionReconciliationReportTool.cs).

### Added
- Added resilient tenant runtime maintenance, shared invalidation, and secret-free SuperAdmin diagnostics. See [runtime options](BancoAlimentar.AlimentaEstaIdeia.Sas.ConfigurationProvider/TenantRuntimeOptions.cs), [revision coordination](BancoAlimentar.AlimentaEstaIdeia.Sas.ConfigurationProvider/RuntimeCacheInvalidationService.cs), [asset refresh](BancoAlimentar.AlimentaEstaIdeia.Sas.Core/HostedServices/TenantStaticSyncHostedService.cs), and [two-tenant HTTP tests](BancoAlimentar.AlimentaEstaldeia.Web.IntegrationTests/IntegrationTests/TwoTenantHttpIsolationTests.cs).
  - **Context:** Startup configuration still blocked threads, one invalid tenant could block healthy tenants, assets refreshed only at startup, and cache reloads affected only one instance. Configuration changes are infrequent, making 15-second revision polling unnecessary.
  - **Options considered:** Keep manual per-instance reloads, introduce a separate distributed cache, or publish environment-scoped revisions in the existing infrastructure database. Compare 15-second, five-minute, and 24-hour polling. For assets, retry whole startup passes or use independent per-tenant schedules.
  - **Decision:** Use asynchronous configuration loading with a 10-second deadline and five-second-to-one-minute retry backoff; isolate tenant-specific client failures. Refresh successful tenants every 24 hours and retry failures independently while preserving cached files. Publish revisions durably and poll every 24 hours in web and function hosts, allowing positive intervals up to one day; expose only identifiers, timestamps, and failure categories to SuperAdmin. Keep authentication-provider enablement unchanged.
  - **Rollout:** Apply [RuntimeCacheInvalidation](BancoAlimentar.AlimentaEstaIdeia.Sas.Model/Migrations/20261121121253_RuntimeCacheInvalidation.cs) once per shared infrastructure database, after earlier pending migrations and before deploying these workers. No tenant data is rewritten and no tenant application database requires this table. Configure all peer instances with the same infrastructure database and environment; publish settings reload after changing secrets or registry metadata. The initiating instance reloads immediately, but peers may retain old settings for up to 24 hours; restart all instances or configure a shorter interval for urgent changes. Review [host-level limits and operational guidance](Documentation/Tenant-Configuration.md), including staging/backup disk space for asset refresh.
- Added the read-only paired-environment [EasyPay subscription reconciliation report](Documentation/EasyPay-Subscription-Reconciliation-Tool.md) to the Tools project.
  - **Context:** The site now configures retries and tracks failed recurring captures, but subscription state and database impact need auditing across the developer/test and production/prod environment pairs before any manual reconciliation.

  - **Rollout:** Configure the two target sections with read-only database/provider credentials and run the documented command. No migration or database update is required. Lifetime/unlimited-payment policy remains a separate business decision.
